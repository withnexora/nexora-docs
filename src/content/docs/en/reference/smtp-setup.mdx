## 1. Document scope / Scope

NEXORA has two groups of emails that need to be distinguished. **Supabase Auth email** includes confirmation email, magic link and password reset managed by Supabase Auth. **NEXORA's transactional emails** include order status notifications, cancellation/return requests, and transactional email templates managed in the Command Deck. These two groups can use different configurations.

NEXORA only sends emails from the backend. SMTP password, Resend API key, Supabase service-role key and JWT secret are not included in HTML, browser JavaScript, `VITE_*`, GitHub or public files.

NEXORA supports two separate email groups. **Supabase Auth email** covers confirmation, magic-link and password-reset messages managed by Supabase Auth. **NEXORA transactional email** covers delivered-order notifications, cancellation/return status messages and editable transactional templates managed in the Command Deck. These groups may use different provider settings.

NEXORA sends emails only from the backend. SMTP passwords, Resend API keys, Supabase service-role keys and JWT secrets must never be placed in HTML, browser JavaScript, `VITE_*` variables, GitHub or public documentation.

## 5. Configure SMTP / Configure SMTP

### 5.1 Basic SMTP parameters / Basic SMTP parameters

Normally, port `465` uses TLS upon connection and the NEXORA backend sets `secure: true`. Port `587` usually starts with an unencrypted connection at the TCP layer and then upgrades via STARTTLS; NEXORA backend sets `secure: false` for this port so that Nodemailer can handle STARTTLS according to the provider configuration. Please prioritize the supplier's official specifications.

Typically, port `465` uses TLS immediately and NEXORA sets `secure: true`. Port `587` commonly starts with a plain TCP connection and upgrades through STARTTLS; NEXORA sets `secure: false` for that port so Nodemailer can negotiate STARTTLS according to the provider. Prefer your provider's official settings.

```ini
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=replace-on-server-only
EMAIL_FROM_ADDRESS=NEXORA <no-reply@example.com>
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=no-reply@example.com
SMTP_PASSWORD=replace-with-mailbox-password
```

In Admin, select **transactional mode = SMTP**, enable **transactional email**, enter sender name and public site production URL, then enable each template you want to use. Secrets are not displayed again after saving; If you suspect password leak, change the password at the provider and update the secret server.

In the Admin, choose **transactional mode = SMTP**, enable **transactional email**, set the sender name and produce public site URL, then enable only the templates you want. Secrets must not be displayed again after saving; If a password may have leaked, rotate it at the provider and update the server secret.

## 14. Error handling / Troubleshooting

### `serverReady: false`

Check `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `EMAIL_FROM_ADDRESS` and the variables of the selected mode. Make sure you restart your Node application after changing the environment.

Check `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `EMAIL_FROM_ADDRESS` and the variables for the selected mode. Restart the Node application after changing environment variables.

### SMTP timeout or connection refused

Check `SMTP_HOST`, port, outbound firewall, TLS mode, username and password. Port 465/587 is not always open by hosting; Ask your hosting provider if the connection is blocked.

Check `SMTP_HOST`, port, outbound firewall, TLS mode, username and password. Hosting providers do not always allow ports 465/587; contact the host if the connection is blocked.

### `535 Authentication failed`

The mailbox password may be wrong, the provider requires an app password, or the account may not have SMTP submission enabled. Create app password according to provider if required; Do not use the main account password if the provider recommends an app password.

The mailbox password may be wrong, the provider may require an app password, or SMTP submission may be disabled. Create an app password when required; do not use the primary account password when the provider recommends an app password.

### Email goes to spam or is rejected

Check sender domain, SPF, DKIM, DMARC, `EMAIL_FROM_ADDRESS`, reverse DNS if required by provider and provider delivery logs. Don't try to solve it by randomly changing the subject or sending multiple times.

Check sender domain, SPF, DKIM, DMARC, `EMAIL_FROM_ADDRESS`, reverse DNS if required and provider delivery logs. Do not try to fix deliverability by randomly changing subjects or repeatedly resending.

### Email link points to localhost

Edit `public_site_url` in `email_delivery_settings` with HTTPS production domain. Also edit Supabase Site URL/Redirect URLs and check the frontend/backend environment variables are pointing to the correct origin.

Set `public_site_url` in `email_delivery_settings` to the production HTTPS domain. Also update Supabase Site URL/Redirect URLs and verify that frontend/backend environment values ​​point to the correct origin.

### Template does not send even though SMTP is configured

Check the template's `transactional_enabled`, `is_enabled`, event type, queue status and dispatch permissions. The `skipped` state usually means that the system is actively not sending because the safety conditions are not sufficient.

Check `transactional_enabled`, the template's `is_enabled`, event type, queue status and dispatch permission. A `skipped` status usually means the system intentionally did not send because a safety condition was not met.
